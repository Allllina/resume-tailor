# 通用简历优化规则

## Bullet Point 核心公式

**Accomplished [X] as measured by [Y] by doing [Z]**

即：**成果 [X]（用 [Y] 量化） + 通过什么方法 [Z] 达成**

### 关键原则：结果前置

用一个 Active 的动词开头，且最好是结果导向型动词。先让筛选者看到你达成了什么，再解释你怎么做到的。筛选者平均30秒扫一份简历，结果放前面才能抓住注意力。

### 三个组成部分

1. **[X] 成果**：用强动词开头，直接点明你达成了什么（Improved / Increased / Reduced / Built / Launched）
2. **[Y] 量化**：用数字衡量成果的大小（可以是绝对值，也可以是和基准的对比）
3. **[Z] 方法**：补充细节，说明你用什么方法/手段达成了这个结果

### 对比示例

**一般写法（没有公式）：**
- ❌ "Studied financial performance of companies and made investment recommendations."
- ❌ "负责用户调研工作"

**高级写法（使用公式）：**
- ✅ "Improved portfolio performance by 12% ($1.2M) over one year by refining cost of capital calculations for information-poor markets and re-weighting portfolio based on resulting valuations."
- ✅ "提升NPS 12分，通过主导3轮用户深度访谈（N=45，覆盖新用户/活跃/流失三类人群），产出用户旅程地图并推动产品侧落地5项体验优化"

### 中文简历的灵活运用

中文语法和英文不同，不必死板套用英文语序。两种都可以：

**结果前置式（优先推荐）：**
> 提升注册转化率50%（从18%到27%），通过漏斗分析定位3个关键流失节点并推动产品侧完成5项交互优化

**动作开头+结果收尾式（也可以）：**
> 通过漏斗分析定位注册流程3个关键流失节点，推动产品侧完成5项交互优化，注册转化率从18%提升至27%

两种写法都OK，核心是：**每条 bullet 必须有量化结果，且结果要在显眼位置**。

## Bullet 闭环硬规则（与 quality-pass.md Pass 3 source-grounding 联动）

以下三条是**bullet 写作的硬规则**，违反 = 不可发布，必须重写。

### 1. 独立 STAR 闭环
**每条 bullet 必须是单一项目 / 单一情境 / 单一动作 / 单一结果的独立闭环。**

- 不允许一个 bullet 横跨两个项目（如把"欧洲战略复盘 + 低空经济"合 1 行）
- 不允许一个 bullet 同时讲两段经历的内容
- Cat 3 supporting 即使预算紧张也只能讲 1 个项目；如果一段经历值得 supporting 但只能选 1 个项目代表，就只代表 1 个，**宁可少写一个项目，也不混讲**
- 单一情境内可以串联 [Action → Method → Outcome]，但不能跳到第二个情境

**自检：** "这条 bullet 砍掉前后文，单独读，能否 1 句话讲完一件完整的事？" 不能 → 拆。

### 2. 业务闭环 4 段式（Cat 1 / Cat 2 强制；Cat 3 推荐）

**核心论断：** 在面试官眼里，"提升 30% 效率" / "模型准确率 0.9" 如果没有业务场景支撑全是废话。**bullet 的价值不来自"我做了什么 + 多少 metric"，而来自"我推动了什么业务闭环"。**

#### 4 段式结构

每条 Cat 1 / Cat 2 bullet 必须含以下 4 个元素中至少 **3 个**：

```
[业务场景：客户 / 业务方面临的具体决策问题]
  → [Action：你做了什么具体分析 / 工作]
  → [Insight：你识别了什么非显然的判断 / counter-intuitive 事实 / 关键证据]
  → [Recommendation 或业务结果：你推动业务方做了什么 / 带来了什么具体业务影响]
```

**Insight 是核心价值锚点**——它证明你不是堆资料的人，而是有判断力。光有 Action + Recommendation 没有 Insight = 普通工人；光有 Insight 没有 Recommendation = 嘴炮分析师；都没有 = 流水账。

#### 范例库（参照 user 提供的 4 个范本）

**业务派范例（电商 / 增长 / 直播——业务结果可观察的场景）：**

> **库存看板：** 针对电商业务的库存积压问题，搭建 SKU 周转监控看板。通过计算"库销比"识别出 15% 的呆滞 SKU，并及时建议运营启动定向出清策略，将整体仓储成本降低了 10%。

> **流失预测：** 通过流失模型识别出高风险客群，发现核心流失诱因是竞对低价拦截，基于此建议营销侧对该客群精准投放"满减"而非"折扣券"，通过 AB 测试验证，该策略成功挽回了 5% 的流失。

> **AB 测试：** 针对 Coupon ROI 低迷，提出阶梯门槛券替换"无门槛券"。逻辑是筛选出处于"犹豫区间"的用户（即差 10-20 元凑单的人群）。实验证明，该策略在预算不变的情况下，将平均客单价（ARPU）提升了 12%。

> **直播间分析：** 拆解直播间人货匹配漏斗。发现流量峰值期 GMV 未达标，原因是高客单价商品承接力不足。通过调整"引流款-利润款"的切货节奏，实现了直播间每小时 GMV 15% 的爆发。

**咨询 / 研究派范例（无可观察业务结果的场景，见下文 carve-out）：**

> **咨询 demo：** 承担头部封测企业（OSAT）"未来 5 年应押注哪个下游赛道"的核心战略问题中下游应用研究模块，对比汽车 / AI 计算 / 存储 / AI 终端 4 类下游对先进封装的需求差异；**识别出 AI 计算虽增速最快但被 Foundry 主导封装、OSAT 进入需差异化能力，而汽车赛道虽增速温和、车规认证周期与可靠性要求恰构成 OSAT 通过能力积累可建立的壁垒**；据此建议客户聚焦汽车 + 存储两条 OSAT 能形成壁垒的赛道，AI 计算作差异化机会保留观察。

#### 咨询 / 研究 / 学术项目的 carve-out

**当业务结果客观不可见时**（咨询交付报告 → 客户内部决策周期 6-24 个月，实习生看不到结果 / 学术研究无业务 metric）：

允许用 **Insight + Recommendation** 替代业务结果，**但必须满足**：

1. **Insight 是 counter-intuitive / 非显然的判断**——不是"识别出 4 类下游差异"（这是 Action），而是"识别出 AI 计算市场最大但不该聚焦投，汽车看似不性感但有壁垒"（这是 Insight）
2. **Recommendation 是 actionable 的具体路径**——不是"提出战略建议 / 完成报告"（weasel），而是"建议聚焦 X + Y 两条赛道，AI 计算保留观察"（具体到客户能听懂的下一步动作）
3. **业务场景必须前置**——不是"承担研究模块 + 输出 longlist"（缺场景），而是"针对客户'押注哪个赛道'的战略问题 + ..."

**仍然禁止：**

| 禁止类型 | 反例 |
|---|---|
| 空泛过程语言 | "完成 12 维竞争格局分析" / "覆盖 30 家企业对标" / "产出 50 页报告" |
| 客户行为宣称 | "客户基于此做出 go/no-go 决策" / "客户采纳建议" |
| Weasel 灰色语言 | "进入客户正式交付物" / "成为项目核心输出" / "作为重要参考意见" |
| 模型 metric 当业务结果 | "AUC=0.85" / "RMSE=32%" / "HR=1.274" 单独使用——如要写需绑定到业务问题（"识别 X% 假阳性，避免下游策略错配"） |

#### 自检（三问）

1. **业务场景问：** 这条 bullet 在解决谁的什么具体业务问题？ 答不出 → 重写第一段加场景
2. **Insight 问：** 这条 bullet 体现的是工作量、还是非显然的判断？ 工作量 → 想想真正的 Insight 是什么
3. **闭环问：** Insight 之后我推动了什么具体动作？ 没有 → 这是观察不是闭环，要么补 Recommendation，要么承认 Cat 3 supporting

**业务派**：4 段全占，业务结果用 metric。
**咨询/研究派**：3 段（场景 + Insight + Recommendation），业务结果可缺。
**项目段（学术 / 个人项目）**：可加"方法可迁移至 X 业务场景"作业务可应用性的 layered outcome。

### 2.5 行业 Insight 简化原则（v0.3.3 校准）

**简历是 hook，面试是展开。** 行业 specific 洞察应留给面试展开，不在简历显化。

| 简历显化层级 | 状态 |
|---|---|
| ✅ **始终展示**：业务场景 + Action + Outcome / Deliverable | 必须 |
| ✅ **可保留**：通用方法论 / 框架（5 维评估、3 层模型、4 段式断点 等可迁移） | 推荐 |
| ⚠️ **谨慎使用**：跨行业 generic insight（"根因在端到端场景未打通" 等）| 1 段 bullet ≤1 处 |
| ❌ **删除**：行业 specific 洞察（"AI 计算被 Foundry 主导封装"、"CTX 使用为路径驱动而非疾病驱动"、"设备租赁推动医院付费模式从 X 转向 Y"等） | 行业不对口时必删 |

**两个判断标准**：

1. **目标岗位行业是否与该 insight 行业一致？** 不一致 → 删（米哈游招聘人不会对半导体封装 / 医疗器械付费模式有兴趣）
2. **该 insight 是否要留给面试 probe？** 投递岗位面试官 likely 会问 "这个项目你最大判断是什么"——如果你这条全摆简历上，面试反而无可讨论

**典型违规 + 修正：**

> ❌ "...对比 4 类下游赛道，**AI 计算被 Foundry 主导封装、汽车车规认证周期反构成 OSAT 壁垒**，建议聚焦汽车与存储"  
> ✅ "...对比 4 类下游赛道**并输出赛道优先级建议**"

> ❌ "...评估各方影响差异，**其中设备租赁推动医院付费模式从'买设备 + 维保'转向'租赁 + 服务打包'，集采 VBP 促使 OEM 将售后从成本中心重新定位为利润中心**"  
> ✅ "...评估对售后业务的影响，6.10 交付中期 Excel、6.16 交付案头政策 PPT"

**与 v0.3.2 业务闭环 4 段式的关系**：
- v0.3.2 把 4 段式（场景 + Action + Insight + 结果）作为咨询场景的硬规则——但对**跨行业投递**（你 80% 的场景）这条规则反而把不相关的行业判断推到简历前台
- v0.3.3 校准：4 段式中 Insight **是 optional**，由"目标岗位行业 fit"决定显化与否
- 投同行业（咨询投咨询、投研投投研）→ Insight 显化是优势
- 投跨行业（咨询投互联网 / 游戏 / AI）→ Insight 应隐藏，让 Action + Method + Outcome 撑住

### 3. Source-grounding（每条 bullet 必须可溯源）
**每条 bullet 的所有事实陈述（数字、名字、动作、结果）都必须可在以下三类合法 source 之一中找到对应来源：**

| 合法 source | 用途 | 注入规则 |
|---|---|---|
| `assets/experience-bank/raw/*.md` | 实习 / 项目 / 真实经历的事实 | 直接 cite 段落即可 |
| `assets/profile/user-profile.md` | 候选人画像、教育、技能栈、口头补充 | 直接 cite 段落即可 |
| `assets/knowledge-base/references/speedlearn-whitelist.json` | 用户没掌握但**已批准 3 天内可速成**的技能 | 仅技能栏 / Skills section 注入；不允许以此为 source 写 experience bullet 中的"我用过 X 做了 Y" |

- 写每条 bullet 时**先读源文件**，再写 bullet——不允许从 user-profile 索引的"一句话总结"凭印象生成内容
- 找不到来源 → 标 `[待补充]` 或删除，**绝不**用"这种岗位 / 这种学校通常..."类训练数据推断填充
- 由 `quality-pass.md` Pass 3 反向 verify 每条 bullet 的事实是否在源文件中存在
- speedlearn whitelist 的入库 protocol 见 `quality-pass.md` Pass 3 § JD-triggered Speedlearn 流程

> **典型违规案例（来自 2026-04-26 试跑）：** Kearney bullet 写 "运用 12 维竞争格局分析与 3 类战略路径推演" —— 12 维 / 3 类是数据，但源文件 `01-kearney.md` 中并无；这是凭"咨询项目通常会有 X 维框架"凭印象编的，违反规则 3。
> **典型违规案例：** Kearney bullet 写 "用 Python 自动化抽取关键政策条款" —— 源文件中 Kearney 项目无任何 Python 使用记录；这是为了"在实习段塞 Python 关键词"凭印象编的，违反规则 3。Python 应由 Projects 段（真实使用场景）承载，而非硬塞进实习段。

## Bullet 六元素解构（XYZ 公式的展开）

XYZ 公式是简化口诀；高密度 bullet 通常包含以下六个元素中的 4-5 个，weave 进 1.5-2 行的可扫读句子。每条 bullet 必须服务以下三个目标至少一个，否则应被剪掉或重写：①证明 competency model 中的某个能力；②强化候选人叙事；③提升 ATS / AI 关键词命中。

| 元素 | 作用 | 例 |
|---|---|---|
| Action verb | 信号 ownership 等级 | Led / Built / Designed / Analyzed / 主导 / 搭建 / 拆解 |
| Context / problem | 为什么这件事重要 | "...to address declining user retention" / "针对续约率连续两季下滑" |
| Method / approach | 如何做（分析 / 技术信号） | "...using cohort analysis in SQL" / "基于生存分析与离职文本挖掘" |
| Contribution | 候选人个人具体做了什么 | "...designing the segmentation logic and dashboard" / "设计分层逻辑并搭建看板" |
| Outcome | 业务影响 | "...reducing churn by 12%" / "续约率提升 8pp" |
| Scale indicator | scope（团队 / 金额 / 用户量 / 区域） | "...across 3 markets" / "覆盖 1,200 FTE" |

**最低要求：** action + 做了什么 + 为什么重要（业务或岗位相关性）。
**高密度目标：** 4-5 元素 weave 进单句 1.5-2 行可扫读 bullet。

### 优先级类别决定 bullet 数与长度（与 `workflow/rewrite-methodology.md §3` 的四档分类对应）

| 优先级 | 单段 bullet 数 | 单条长度 |
|---|---|---|
| Category 1（lead and expand） | 4-6 | 1.5-2.5 行 |
| Category 2（keep but compress） | 2-3 | 1-2 行 |
| Category 3（supporting signal） | 1 | 1 行 |
| Category 4（remove） | 0 | — |

整份简历长度（与 `market-contexts/` 一致）：
- North America：<10 年经验 1 页，senior 最多 2 页
- Mainland China：1-2 页（平台格式可能更受限）
- Hong Kong：2-3 页（CV 格式可接受）

### Bullet 最终自检清单

输出每条 bullet 前过一遍：
- [ ] 是否以强且准确的 action verb 开头？
- [ ] 是否含至少一个角色相关关键词？
- [ ] 候选人能否就这条在面试中讲 2 分钟？
- [ ] 是否服务于简历叙事？
- [ ] 招聘人能在 3 秒内 get 到相关性？
- [ ] 是否无空泛副词与通用语言？
- [ ] 长度是否匹配优先级类别？

### Role-specific 元素排序差异（重要）

上述 6 要素是**通用版本**，适用于 engineering / strategy / data 等 lens。但**产品岗位 bullet** 必须调整元素顺序：

| Lens 类型 | 6 要素优先顺序 | 主导信号 |
|---|---|---|
| **Engineering / Data / Strategy** （Lens A/B/D/HC）| Action verb → Method → Contribution → Outcome → Scale → Context | 执行 + 量化 |
| **产品 / 产品运营 / AI 产品**（Lens C）| **Problem framing → Hypothesis → Design trade-off → Method → Outcome → Tech stack（末位）** | **判断力 + 执行支撑** |

**为什么不同**：产品 HM 扫简历时回答的核心问题是"这个人想清楚再做，还是别人 ask 什么就做什么"。开头是 "Built X using Y" 暗示后者；开头是 "Identified that X caused Y, hypothesized Z" 暗示前者。

**产品岗位 bullet 写作规则**：
- 前 60-70% 文字 = 判断力信号（用户痛点 / 假设 / 设计 trade-off）
- 后 30-40% = 执行（method / tech / outcome）
- 写不出判断力部分的 bullet，**不写**——即使执行很 impressive。宁可少 1 条，也不写一条 engineer-flavored 的纯执行 bullet

详细的产品 lens 判断力 hierarchy 见 `role-lenses/C-product-ops.md` § 0；AI 产品的 6 要素具体化 + 模型 / Prompt / Eval 加分项见 `scenarios/ai-innovation.md` §1-3。

## 量化原则

### 必须量化的维度
- **规模**：用户量、GMV、数据量、项目金额、团队人数
- **效果**：增长率、转化率提升、成本降低、效率提升
- **时间**：项目周期、提前完成的程度
- **排名/对比**：在多少人中排第几、超过多少竞品

### 量化技巧
- 没有绝对数字时用相对数字："提升30%"、"缩短50%"
- 没有精确数字时用合理估算："服务100+客户"、"日均处理10万+条数据"
- 用对比制造冲击力："将原本需要3天的流程缩短至2小时"
- 多维度叠加："覆盖5个城市、30家门店、200+SKU"

### 量化禁区
- 不编造数据，宁可用定性描述
- 不夸大到不可信的程度
- 涉及公司机密的数据用模糊处理："营收规模数亿级"
- **不做过程量化**：「调研7家企业」「对标7家标杆」「提炼7条经验」只说明工作量，不体现impact。量化应聚焦在结果和业务影响上（如"产出方案推动客户启动专项""结论直接用于定价策略"），而非研究过程中查了多少资料

## 动词选择

### 强动词表（按能力类型）

**领导力**：主导、牵头、统筹、搭建、推动、带领、组建、发起
**分析力**：拆解、诊断、洞察、挖掘、建模、量化、归因、评估
**执行力**：落地、交付、完成、达成、实现、推进、迭代、上线
**创新力**：首创、开拓、从0到1搭建、设计、创建、探索、孵化
**沟通力**：对齐、拉通、协同、汇报、提案、路演、谈判

### 动词去重规则
- **同一动词在整份简历中最多出现 2 次**，超过则必须替换为同义强动词
- 高频易重复动词及推荐替换：
  - Built → Constructed / Developed / Engineered / Architected / Assembled
  - Led → Spearheaded / Directed / Headed / Drove / Steered
  - Managed → Oversaw / Coordinated / Orchestrated / Administered
  - Created → Designed / Devised / Produced / Launched / Established
  - Analyzed → Assessed / Evaluated / Examined / Dissected / Investigated
- 输出前必须全文检查动词频率，发现 ≥3 次的动词立即替换

### 项目（Projects）section 格式规则
- 项目 bullet **不使用粗体标签前缀**（如 ~~\textbf{AI Agent Development:}~~），直接以动词开头
- 实习经历 bullet 保留粗体标签前缀（如 \textbf{Driver-Based Market Sizing:}），因为实习内容需要主题分类帮助快速扫读
- 项目标题已经通过 \projheader 提供了上下文，bullet 内部不需要再重复项目名或项目类型

### Bullet 粗体标签（模块标题）长度硬规则

**规则：实习 bullet 的粗体标签前缀（`\textbf{...：}` 内的中文）≤ 6 个字，且必须是「名词 + 动作」结构。**

**为什么 6 个字**：
- 标签的作用是让 reviewer 在 1.5 秒内 scan 出"这条 bullet 讲什么主题"，超过 6 个字眼睛会从 scan 切到 read，反而拖慢节奏
- 标签太长会和后面的正文连成一长行，"主题分类 + 内容"的视觉分层被破坏
- 6 字以内逼迫提炼到关键名词 + 关键动作，模糊或过度限定语自然被砍掉

**为什么"名词 + 动作"**：
- 纯名词标签（如 "指标体系" / "政策竞争"）只交代了主题、没交代候选人在干什么——reviewer 必须读完正文才能 get 你是研究 / 优化 / 搭建 / 评估，scan 效率反而比长标签更差
- 动作锚定 ownership 信号：「指标体系**优化**」「半导体**研究**」「政策**研究**」让 reviewer 1 秒内 get 到"她做了 X 类工作"
- 动作动词同时帮助 ATS 命中关键词（搭建 / 优化 / 研究 / 复盘 / 分析 / 归因 / 测算）

**常用动作动词库**（按工作类型）：

| 工作类型 | 动作动词 |
|---|---|
| 研究 / 分析 | 研究、分析、调研、复盘、对标、拆解 |
| 设计 / 搭建 | 搭建、设计、构建、优化、迭代、改造 |
| 量化 / 建模 | 测算、建模、归因、评估、诊断、验证 |
| 战略 / 决策 | 规划、推演、研判、决策、筛选 |

**典型违规 → 修正**：

| ❌ 违规（字数 / 问题）| ✓ 修正（字数 / 结构）|
|---|---|
| 具身机器人赛道研究（9 / 超长）| 机器人研究（5 / 名词 + 研究）|
| 半导体下游应用与并购研究（11 / 超长）| 半导体研究（5 / 名词 + 研究）|
| 指标体系与跨组织数据策略（11 / 超长）| 指标体系优化（6 / 名词 + 优化）|
| 市场规模测算与用户分层（10 / 超长）| 市场测算（4 / 名词 + 测算）|
| 业务执行差距复盘（8 / 超长）| 执行复盘（4 / 名词 + 复盘）|
| 用户分层与市场规模测算（10 / 超长）| 用户分层（4 / 名词 + 分层）|
| 政策与竞争对手动态分析（10 / 超长）| 政策研究（4 / 名词 + 研究）|
| 指标体系（4 / 缺动作）| 指标体系优化（6 / 加动作）|
| 政策竞争（4 / 缺动作）| 政策研究（4 / 加动作）|
| 半导体并购（5 / 缺动作）| 并购筛选（4 / 加动作）|

**两个例外**：
1. 英文标签（如 \textbf{Driver-Based Market Sizing:}）按英文 ≤4 词判断，不卡 6 字
2. 缩写 / 专有词（如 \textbf{PSM + Cox 归因：}）按"语义单元"算，PSM / Cox 是单个 token，不拆字计数

**自检（双层检查）**：
1. **字数**：写完每条 bullet 后扫一眼粗体前缀，数中文字数。**> 6 字必须重写**，不接受"差一两个字没事"的妥协
2. **结构**：能不能在标签里圈出一个动作动词？没有 → 加（或换更紧凑的动词把字数挤出来）

这是版式硬规则，不是建议。

### 动词禁区
- 避免弱动词："参与"、"协助"、"帮助"、"负责"（太被动）
- 避免口语化："搞了一个"、"做了一些"
- "负责"可以用，但后面必须跟具体成果，不能只说"负责XX项目"

## 中英文混排规范

### 适用场景
投递跨国公司（如科尔尼、麦肯锡中国、宝洁等）时，简历中适当使用英文术语体现专业性。

### 规则
- **专业术语保留英文**：ROI、DAU、MAU、GMV、NPS、A/B Test、OKR、P&L、MECE、MVP
- **岗位名称可中英对照**：产品经理 (Product Manager)
- **公司名和品牌名用英文原名**：Kearney、McKinsey、ByteDance
- **整句不要中英夹杂**：不要写"我lead了一个team去deliver这个project"
- **一致性**：全篇统一，要么全用"用户"要么全用"User"，不混用

## 简历整体原则

### 输出导向
- 每条经历必须有结果，没有结果的经历不值得写
- 先写结果再补充过程，结果放在 bullet 最显眼的位置

### 隐性表达
- 不直接声称能力："具有优秀的沟通能力" ❌
- 用事实证明能力："跨4个部门协调资源，推动项目在2周内从立项到上线" ✅

### STAR 变体
适用于所有方向，但各方向侧重点不同：
- **S**ituation：简要交代背景和挑战（一句话）
- **T**ask：你的角色和职责（隐含在动词中）
- **A**ction：具体做了什么（三段式的中间部分）
- **R**esult：成果（三段式的最后部分）

### 篇幅控制
- 每段经历 3-5 个 bullet points
- 每个 bullet 1-2 行，最多不超过3行
- 最重要的经历放最多 bullet，次要的精简到2-3个

### 排序逻辑
- 每段经历中，最亮眼的 bullet 放第一条
- 经历按相关性排序，不一定按时间倒序
- 如果某段经历与目标岗位高度相关，即使较早也可以提前

## 常见问题修复模板

| 问题类型 | 原文示例 | 优化方向 |
|---------|---------|---------|
| 缺少成果 | "负责用户运营工作" | 补充量化成果 |
| 过于笼统 | "参与多个项目" | 具体化：几个项目、什么领域、什么角色 |
| 被动语态 | "被分配到XX项目" | 改为主动："主导/承担XX项目" |
| 堆砌职责 | 列了8个"负责XX" | 精选3-4个最有成果的，深写 |
| 缺少上下文 | "提升了转化率" | 补充：从多少到多少、什么渠道、多长时间 |
| 自我评价式 | "学习能力强" | 删除，用经历证明 |
| 方法论堆砌 | "通过结构化桌面研究与多维度竞争基准对标，评估关键领域增长潜力" | 用具体事实替代方法论名词：研究了几个领域、对标了什么维度、发现了什么结论。尤其注意政策研究/产业规划类项目容易掉进这个坑 |
